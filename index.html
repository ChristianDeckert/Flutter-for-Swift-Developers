Classes, and what replaces structs

This is the Book from the example app, now with the extras a Swift struct gives you for free. Dart has no structs. Every value is an object passed by reference, and assigning it never copies it. You get struct-like behaviour from an immutable class: final fields, a const constructor and a copyWith method that returns a changed copy. Two instances are equal only if you override == and hashCode; the default compares identity.

    required this.id,

    required this.author,
    required this.copies,

  });

  // A named constructor, Dart's second init.

  final int id;
  final String title;
  final String author;
  final int copies;
  final double price;
  final String? note;

    title: title,
    author: author,

    price: price,

      other.id == id &&
      other.title == title &&

      other.copies == copies &&

  final Object error;
}

void report(SaveResult result) {
  // Remove one case and the compiler reports that the switch is not exhaustive.

How layout works

Flutter's rule is short: constraints go down, sizes go up, the parent sets the position. A parent tells each child the minimum and maximum size it may take, the child picks a size within that range, and the parent places it. This is close to SwiftUI's size proposals, but stricter, and it explains the three errors you will meet in the first week.

  • “A RenderFlex overflowed by 42 pixels”A Row or Column has more content than room, shown as yellow and black stripes. Wrap the child that should shrink in Expanded or Flexible, or let text ellipsize.
  • “Vertical viewport was given unbounded height”A ListView sits inside a Column, which allows unlimited height. Wrap the list in Expanded, or make the whole page one CustomScrollView.
  • A Container fills the whole screenWithout a child or size, a Container expands to its constraints. Give it a size, or use SizedBox for gaps.

Lifecycle and footguns

Swift frees an object the moment its last strong reference goes away, and you clean up in deinit. Dart has neither: memory is freed by a garbage collector at some later point, and nothing runs when an object dies. Cleanup in Flutter is therefore explicit and tied to lifecycle methods. This section shows those methods and the mistakes that cost the most time.

Memory: a garbage collector instead of ARC

A tracing garbage collector keeps every object that can still be reached from a root: a global or static field, a running timer, an open stream subscription, the widget tree. Everything else is collected, including reference cycles. That is why you never write [weak self].

What leaks in Dart is not a cycle but a forgotten registration. The example below listens to syncService, an app-wide ChangeNotifier: Flutter's simplest observable object, which keeps a list of listener functions and calls them all from notifyListeners(), much like an ObservableObject. If a long-lived object holds your closure, the closure holds this, and this holds its widget, its context and everything it references. The Swift rule “break the cycle” becomes “unregister what you register”.

Footguns

Each card starts with what you see when it goes wrong, so you can search this page for the error text.

Lifetime

Using a State after its screen closed

SymptomsetState() called after dispose() or Looking up a deactivated widget's ancestor is unsafe.

An await, timer or stream callback finished after the user left the screen. Write if (!mounted) return; after every await in a State, or if (!context.mounted) return; where you only have a context. Cancel timers and subscriptions in dispose so their callbacks never run late.

Not disposing what you created

Symptom… was disposed with an active Ticker. or no error at all, while memory grows and old callbacks keep firing

Every TextEditingController, AnimationController, ScrollController, FocusNode, Timer, StreamSubscription and AppLifecycleListener you create needs a matching line in dispose, before super.dispose(). Controllers passed in from outside belong to whoever created them; do not dispose those.

Listening to something that outlives you

SymptomA screen you closed still reacts to events, or setState() called after dispose() appears long after it closed

A long-lived service, global stream or ChangeNotifier holds your listener, and with it the whole State. Remove it in dispose with the same function you added.

Reading late too early

SymptomLateInitializationError: Field '_controller' has not been initialized.

late moves the null check from compile time to runtime. Assign late final fields in initState, before anything in build can read them, or make the field nullable when it really is optional.

Rebuilds

Creating things inside build

SymptomA text field loses its text, an animation restarts, or a FutureBuilder flashes its loading state on every rebuild

build runs often, up to once per frame during an animation. A controller, Future or Stream created there is a new object each time. Create it once in initState and keep it in a field.

Copying the widget's input into the State

SymptomThe parent passes a new value, but the screen keeps showing the old one

initState runs once. A field set from widget.loan there never sees the next loan. Read widget.loan directly in build, or update the copy in didUpdateWidget.

Lists without keys

SymptomAfter deleting or reordering a row, another row shows the deleted row's text, checkbox or animation

Without keys Flutter matches widgets to State by position. Give list items key: ValueKey(item.id). The reverse also works on purpose: changing a key, such as key: ValueKey(date), throws the old State away and starts fresh.

Expensive work in build

SymptomScrolling or animations stutter; DevTools shows long build times

Sorting, filtering or formatting large lists in build repeats on every frame that rebuilds. Do it once when the data changes, not in build, and mark unchanging widgets const so Flutter can skip them.

Context

Inherited lookups in initState

SymptomdependOnInheritedWidgetOfExactType<_InheritedTheme>() … was called before initState() completed.

Theme.of, MediaQuery.of and AppLocalizations.of subscribe to changes, which is not allowed before the State is fully inserted. Move the lookup to didChangeDependencies or build.

A context from the wrong level

SymptomScaffold.of() called with a context that does not contain a Scaffold.

X.of(context) searches upward from the widget that owns the context. The context of the widget that builds the Scaffold sits above it. Extract the child into its own widget, or wrap it in a Builder to get a context below.

Tooling and async

Expecting hot reload to rerun setup

SymptomYou changed initState, main or a global initializer, and nothing happens

Hot reload keeps all existing state, so code that only runs at creation does not run again. Hot restart instead: R in the flutter run terminal, or the restart button in your editor.

Futures nobody awaits

SymptomSteps run in the wrong order, and errors appear only in the console, if at all

Calling an async function without await starts it and moves on. Await it, or write unawaited(…) when fire-and-forget is what you mean, so a reader knows it was deliberate.

Not a footgun: closures in loops. Each iteration of a Dart for loop has its own variable, including for (var i = 0; …). Callbacks created in a loop see the value from their own iteration, as in Swift.

Providers and notifiers

Local state lives in a State object. State that several screens share, such as the settings or the signed-in member, lives in Riverpod providers. A provider is a global, lazily created and cached value. Widgets read it through a ref: ref.watch subscribes, like reading an @Observable property in body. A Notifier is your view model, with one difference: you replace its whole immutable state value instead of mutating properties.

To get a ref, a widget extends ConsumerWidget instead of StatelessWidget; its build receives a WidgetRef ref as a second parameter. For local state too, use ConsumerStatefulWidget, whose ConsumerState has a ref field that also works in initState. The whole app sits inside a ProviderScope, which stores the provider values; Layers and injection shows it.

Provider lifecycle

A provider is created the first time something reads it. A plain provider then lives as long as the ProviderScope, which here means the whole app. A provider marked .autoDispose is destroyed when the last widget stops watching it and is created fresh the next time. Inside a provider, ref.onDispose is your dispose.

Flutter · Riverpod
final readingTickerProvider = StreamProvider.autoDispose<int>((ref) {
  final controller = StreamController<int>();
  final timer = Timer.periodic(
    const Duration(seconds: 1),
    (t) => controller.add(t.tick),
  );
  ref.onDispose(() {        // runs when no widget watches any more
    timer.cancel();
    controller.close();
  });
  return controller.stream;
});

Prefer ref.watch, ref.listen and StreamProvider over subscribing by hand in a State: Riverpod removes those subscriptions when the widget goes away, so there is nothing to forget.

/// A colour matrix that boosts saturation, as Apple's glass does.
List<double> _saturation(double s) {
  const r = 0.2126, g = 0.7152, b = 0.0722;
  return [
    r * (1 - s) + s, g * (1 - s), b * (1 - s), 0, 0,
    r * (1 - s), g * (1 - s) + s, b * (1 - s), 0, 0,
    r * (1 - s), g * (1 - s), b * (1 - s) + s, 0, 0,
    0, 0, 0, 1, 0,
  ];
}

Calling native code with a channel

A MethodChannel sends a method name and arguments to Swift or Kotlin and returns a Future with the result. Every plugin on pub.dev, such as share_plus or url_launcher, is a packaged channel. For more than one or two methods, Pigeon generates typed Dart and Swift code from one interface definition, so names and types cannot drift apart.

Swift · ios/Runner/AppDelegate.swift
import Flutter
import UIKit

@main
@objc class AppDelegate: FlutterAppDelegate {
  override func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions:
      [UIApplication.LaunchOptionsKey: Any]?
  ) -> Bool {
    GeneratedPluginRegistrant.register(with: self)

    let registrar = self.registrar(forPlugin: "Accessibility")!
    let channel = FlutterMethodChannel(
      name: "app/accessibility",
      binaryMessenger: registrar.messenger())
    channel.setMethodCallHandler { call, result in
      switch call.method {
      case "reduceTransparency":
        result(UIAccessibility.isReduceTransparencyEnabled)
      default:
        result(FlutterMethodNotImplemented)
      }
    }

    return super.application(
      application, didFinishLaunchingWithOptions: launchOptions)
  }
}

const _accessibility = MethodChannel('app/accessibility');

/// False on platforms that have no such setting.
Future<bool> reduceTransparency() async {
  if (kIsWeb || defaultTargetPlatform != TargetPlatform.iOS) {
    return false;
  }
  try {
    final value = await _accessibility
        .invokeMethod<bool>('reduceTransparency');
    return value ?? false;
  } on PlatformException {
    return false;
  } on MissingPluginException {
    return false; // the Swift side is not registered
  }
}

The channel name is just a string that both sides agree on. Calls are asynchronous and arrive on the main thread on iOS, so keep native work short or move it off the main thread. Where the registration code lives depends on your project template: newer templates that use the iOS scene lifecycle register plugins in a different place, but the channel code itself stays the same.
